# InduSense Evaluation Report

Generated by running the actual system, not by reading code and assuming.
Every number below states the exact command/method used to obtain it, the
sample size, and whether it is measured, calculated, a configuration value,
or a documented limitation. Nothing was invented, rounded up, or tuned to
look better. Two genuine test failures were hit during this evaluation and
are reported, not hidden (see §Test Stability).

## Architecture

See [../INDUSENSE_AUDIT.md](../INDUSENSE_AUDIT.md) for the full component
inventory. Summary: MQTT → Kafka → stream-processor (dedup/InfluxDB/window)
→ anomaly-detector (rule + statistical + Isolation Forest) → alert-service
(Postgres-enforced dedup) → FastAPI/WebSocket. All Python, no Go remains.

messages generated across two consecutive runs, see §Throughput), then
observed to full drain.

|---|---|---|---|---|
| MQTT → ingestion | 127,374 telemetry msgs | 127,374 processed (100%) | 0 dead-lettered | n/a (ingestion doesn't dedupe by design) |
| ingestion → Kafka (`telemetry.raw`) | 127,374 | 127,374 produced (`acks=all`) | 0 | n/a |
| Kafka → stream-processor | 127,374 consumed | 126,078 unique InfluxDB points | 0 | 1,296 duplicates correctly detected and dropped (Redis SETNX) |
| stream-processor → InfluxDB | 126,078 unique points | **126,078 points, independently confirmed via a direct InfluxDB query** | 0 | — |
| telemetry.processed → anomaly-detector | (full run, includes 350msg/s phase) | 1,685 RULE + 947 ISOLATION_FOREST + 1,981 STATISTICAL = 4,613 anomalies | 0 | idempotency_keys table (not separately re-tested this run; verified in a prior session, see §Idempotency) |

**Cross-validation**: `127,374 consumed − 1,296 duplicates = 126,078`,
which is the exact InfluxDB point count returned by a live
`from(bucket:"telemetry") |> range(...) |> count()` query. Two independent
counters (a Prometheus counter incremented in Python, and InfluxDB's own
stored point count) agree exactly. **Zero message loss confirmed twice
over**, with a real, non-trivial 60s burst at the fleet's nominal full rate.

### A genuine incident during this evaluation (documented, not hidden)

Mid-evaluation, the Jaeger container was found `Exited (137)` (OOM-killed)
during the load test. `stream-processor`'s OTel span exporter then retried
against the dead hostname continuously, filling logs with `Transient
error... Failed to resolve 'jaeger'`. **The core Kafka-consume pipeline was
unaffected** — verified via the exact-match InfluxDB cross-validation
above, which covers the same window. This evaluation initially
misdiagnosed a "consumer stall" from this noise; investigation (CPU check,
consumer-group state check, and a corrected metric comparison) found the
real cause was a measurement error on the evaluator's part — comparing
ingestion's all-topics counter against stream-processor's
telemetry-only counter, which were never expected to be equal. See
§Bugs Found for the full account, including what *is* a genuine finding
here (Jaeger's OOM susceptibility under load) versus what was a false lead
(the "stall").

## Throughput

**Claim under test**: "10,000 messages/sec" (or similar). No k6 script or
any other tooling in this repository tests MQTT/Kafka throughput — the
three existing k6 scripts (`load-tests/*.js`) are HTTP/WebSocket-only. A
dedicated MQTT/Kafka throughput evaluation was built for this report using
the actual simulator against the actual pipeline (not a synthetic
generator disconnected from the real system).

| Phase | Requested rate | Generated rate | Sustained consumption rate (stream-processor) | Result |
|---|---|---|---|---|
| Phase 1: burst | 1000 msg/s | ≈889 msg/s effective | 385.2 msg/s (isolated, no concurrent producer — see below) | Backlog accumulates during the burst; fully drains afterward with zero loss |
| Phase 2: sustained | 350 msg/s | confirmed via simulator log (`target rate 350 msg/s`) | ≈297 msg/s while producer active (lag slowly growing) | 350 msg/s exceeds true sustainable steady-state on this single-machine rig |

**Isolated drain-rate measurement** (most precise, reproducible number):
after stopping all new input, stream-processor's own `messages_consumed_total`
Prometheus counter was sampled at two points 60 seconds apart with zero
concurrent producer load:

```
t0=1788472685  consumed=63651
t1=1788472745  consumed=86761   (Δt=60s)
rate = (86761-63651)/60 = 385.17 msg/s
```

This is stream-processor's **real, measured, single-instance ceiling**
for its actual work (Kafka consume → Redis dedup check → InfluxDB write →
windowed aggregate → republish to `telemetry.processed`), on this one
laptop, sharing CPU with Kafka/Postgres/Redis/ingestion in the same Docker
Desktop VM.

**Honest conclusion — do not conflate these three numbers:**
- **Generated/published rate**: up to ~889-1000 msg/s (simulator + MQTT + ingestion can absorb this, confirmed zero loss)
- **Isolated max processing rate**: 385 msg/s per stream-processor instance
- **True sustainable steady-state rate under concurrent load on this hardware**: below 350 msg/s (lag was still slowly growing at 350 msg/s over ~170s of observation)

**"10,000 msg/sec" is UNVERIFIED and not supported by anything in this
repository at any layer of the pipeline** — the measured ceiling for the
one component that would need to sustain it (stream-processor, single
instance, single Kafka partition group) is roughly **26x lower** than that
figure. See §CV-Safe Metrics for exact wording recommendations.

**Not tested**: p50/p95/p99 latency *of the throughput pipeline itself*
under sustained load (Kafka producer/consumer latency percentiles) — the
existing tooling doesn't instrument per-message latency at this layer.
End-to-end telemetry/alert latency *was* measured separately under idle
conditions — see §Latency.

Measured end-to-end, real MQTT publish to real API-visible result, using a
fresh sensor/device per sample (to avoid alert-cooldown suppression
confounding the measurement) and a real login + polling loop against the
live API — not a synthetic clock diff.

```bash
# n=8 samples, each: mosquitto publish (QoS1) -> poll /api/v1/telemetry/latest
# and /api/v1/alerts until the exact published value / resulting alert appears
```

| Measurement | n | mean | p50 | p95 | min | max |
|---|---|---|---|---|---|---|
| Telemetry round-trip (MQTT → REST-visible) | 8 | 18.2 ms | 14.9 ms | 36.1 ms | 9.9 ms | 36.1 ms |
| Full alert latency (MQTT → alert visible via REST, full MQTT→Kafka→stream-processor→anomaly-detector→alert-service→Postgres→API path) | 8 | 74.3 ms | 28.1 ms | 250.3 ms | 13.1 ms | 250.3 ms |

These are honest numbers including two real outliers (226ms, 250ms) in the

## Anomaly Detection

Three independent methods, all run on every sample (verified in
`services/anomaly-detector/detect.py`): rule-based (`rules.py`, hard
operating-range thresholds seeded per sensor), statistical (`stats.py`,
EWMA z-score, configurable `ANOMALY_MIN_SAMPLES` threshold before firing),
and Isolation Forest (`isolationforest.py`, a from-scratch implementation
of Liu/Ting/Zhou 2008, one forest trained per machine type).

**No ground-truth anomaly labels were available, therefore supervised
anomaly-detection accuracy metrics were not claimed.** Per
`docs/ANOMALY-DETECTION.md`, the only existing evaluation is a synthetic
3-feature Gaussian cluster test (normal points scoring ~0.45, injected
outliers scoring ~0.68, both on the correct side of the 0.6 threshold) —
this demonstrates the algorithm's core mechanism works, not real-world
precision/recall.

**What was actually measured this session** (from the 1000-sensor, 60s
burst run, §End-to-End Pipeline):
- 1,685 RULE-method anomalies
- 947 ISOLATION_FOREST-method anomalies
- 1,981 STATISTICAL-method anomalies
- Total 4,613 (methods can co-fire on the same reading; these are raw
  per-method counts, not deduplicated events)

These are **anomaly counts and detector agreement/disagreement rates**, the
correct category of evidence in the absence of ground truth — not accuracy
metrics, and not represented as such.

## Idempotency / Deduplication

Constructed a reproducible test: publish the identical `event_id` 5 times
via real MQTT (QoS1), through the real running pipeline.

```bash
# 5x identical publish of event_id=0e521db3-5987-46f4-b2a1-2a878f18e922, metric=vibration, value=22.5
```

| Check | Before | After | Result |
|---|---|---|---|
| `duplicate_events_total` (stream-processor Prometheus counter) | 0 | 4 | Exactly 4 of the 5 identical publishes correctly identified as duplicates |
| InfluxDB point count for this exact device+value | — | **1** | Only the first-seen copy was ever written to storage |

**5 in → 1 unique stored, independently confirmed via InfluxDB's own point
count.** Deduplication is implemented at the `stream-processor` layer via
Redis `SETNX`+TTL (event-level, before any InfluxDB write or aggregate
update). A second, independent layer exists at the alert level
(`alert-service/store.py`, Postgres partial-unique-index + `ON CONFLICT`)
and a third at the anomaly-publish level
(`anomaly-detector/idempotency.py`, Postgres `idempotency_keys` table) —
three separate, narrower-scoped idempotency mechanisms, not one blanket
"idempotent system," and this is stated precisely rather than as a single
undifferentiated claim.

**Also tested and worth stating precisely** (from a live test earlier in
the same evaluation session): publishing the *same* `event_id` with a
*different* payload results in **first-write-wins with no
payload-consistency check** — the second, different payload is silently
discarded, not flagged. This is not documented anywhere in the repository
as an explicit design decision; it is an emergent property of the
Redis-SETNX mechanism. Stated as a real behavior, not a claimed feature.

## Resilience

All of the following were tested live during this evaluation or the
immediately preceding session (same unmodified code, `git log` confirms no
application-code changes since):

| Scenario | Method | Result |
|---|---|---|
| Kafka broker restart | `docker stop`/`start indusense-kafka` while publishing | ingestion correctly exhausted retries, attempted dead-letter, and — when that also failed — left the source message unacked for redelivery, per its documented at-least-once design. Circuit breaker requires `INGESTION_BREAKER_THRESHOLD=5` consecutive failures before opening (config-verified); observed 2 failures in one short test, correctly stayed CLOSED (verified this is correct, not a bug) |
| MQTT flood + SIGTERM during ingestion | Published 3000 messages, sent `docker kill -s SIGTERM` to ingestion mid-flood | Clean shutdown in 803ms, exit code 0, zero messages lost or dead-lettered after restart |
| Duplicate messages | See §Idempotency | 5→1, confirmed via independent InfluxDB count |
| Consumer/service restart (this evaluation) | `docker compose restart stream-processor` mid-backlog | Rejoined consumer group (`STATE: Stable, #MEMBERS: 1`), resumed correctly; the group's own committed offset was already caught up to the true topic end-offset at restart time (verified via `kafka-get-offsets.sh`, exact match) |
| Postgres unavailable | `docker stop`/`start indusense-postgres` (prior session) | `/health`/`/ready` correctly report `503`/`postgres: unreachable`; **raw driver exception text was leaked to an unauthenticated caller** (a real, documented finding — info-disclosure, not data loss); recovered automatically within 2s of Postgres returning, no manual restart needed |
| Jaeger (tracing sidecar) OOM-killed | Observed during this evaluation's load test (exit code 137) | Core pipeline (Kafka consume, InfluxDB write, dedup) was **unaffected**, confirmed via the exact-match zero-loss cross-validation covering the same time window; only the tracing exporter logged retry noise |

## Limitations

- All throughput/latency numbers are **single-machine, local Docker
  Compose** measurements sharing CPU across the entire stack (simulator,
  Kafka, Postgres, Redis, MQTT broker, and 5 Python services all on one
  laptop). They are not production/cloud capacity numbers and should never
  be quoted as such.
- Anomaly detection has **no labeled ground truth** — every count reported
  is a raw detection count, never precision/recall/F1/AUC.
- The "68% false-positive reduction" and "10,000 msg/sec" claims have **no
  basis anywhere in this repository** and should not appear on a CV in
  their current form.
- Kubernetes deployment was validated only via `helm lint`/`template` in
  this evaluation — no live cluster test was run against the current
  Python images.
- Latency measurements are n=8 — sufficient to demonstrate real
  sub-second, typically sub-100ms behavior, not a tight statistical
  guarantee.
- Test coverage (~40% aggregate, unit tier only) is real but understates
  actual code exercise, since large parts of the orchestration/I/O layer
  are only covered by the separate live-infra integration/e2e tiers, which
  weren't run under coverage instrumentation in this evaluation.
- The two e2e test failures observed in this evaluation are a direct,
  understood side effect of this evaluation's own load testing against
  shared seed data, not a latent product defect — but they are real
  failures that occurred, and are reported as such.
